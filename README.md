# acme-health

Generated by [workshop-demo-generator](../../) — a Twilio workshop demo scaffolded
for **typescript · SDK**.

## Setup

```bash
cp .env.example .env       # fill in Twilio + LLM creds
./run.sh                   # install deps + start backend on :8080
```

Then hit the health check:

```bash
curl http://localhost:8080/health
# {"status":"ok"}
```

## What's inside

```
acme-health/
  src/
    app.ts                 # Express entry — routes, middleware
    observability.ts       # events store + emitEvent + GET /events (always on)
    twilioClient.ts        # Twilio access layer (SDK-or-REST, same interface)
    channels/              # Channels — reusable Twilio primitive
    relay/                 # ConversationRelay — reusable Twilio primitive
    handlers/              # the routes Twilio calls — one per scenario, plus webhook handlers
    prompts/               # one system prompt per scenario
    tools/                 # the tools the agent calls mid-conversation (add-ons' in SHARED_TOOLS)
    data/                  # clearly fake sample data
  wallboard/             # standalone events wallboard (its own React app)
  package.json  tsconfig.json
  .env.example
  run.sh
  README.md
  CLAUDE.md    PROMPT.md    .mcp.json
```

`src/handlers/` holds the routes Twilio calls, with each scenario's system prompt in
`src/prompts/`, its tools in `src/tools/` and its sample data in `src/data/`. All of
them import the Twilio packages above where a package covers the call.
`src/handlers/` lists every router in its index, which `app` mounts.

## Events (§6)

Every integration records what it does to an events store, exposed at
`GET /events`. The store backend is set by `EVENTS_BACKEND` (default `sqlite`,
written to `EVENTS_DB_PATH`, default `events.db`) and is swappable without
regenerating.

```bash
curl 'http://localhost:8080/events?limit=50'
```

## Demo script

1. **Confirm the app boots** — `./run.sh` and `curl :8080/health`.
2. **Show the layering** — open a Twilio package such as `src/channels/` (reusable Twilio primitives), then
   `src/handlers/` (the routes Twilio calls), `src/prompts/` and `src/tools/`.
3. **Walk the customer through the modular pieces** they'd copy into their own repo —
   one Twilio package, one handler with its prompt and tools — and explain the seams.
4. **Trigger the primary flow** — run the interaction each handler serves.
5. **Open the demo UI** at http://localhost:5174 to show live panels
   over WebSocket.
6. **Open the wallboard** at http://localhost:5175, trigger an
   interaction, and click **Refresh** to watch events stream in.
